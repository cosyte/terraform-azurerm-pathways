# alarms

Azure Monitor metric alerts on five of the metrics Pathways serves at `/metrics` on its health endpoint, and what it takes to read them on Container Apps: a health token and a connection string in the Key Vault, a workspace-based Application Insights resource, and the configuration of an OpenTelemetry collector that runs beside the engine. The root module calls it when `alarms_enabled` is true, and gives the collector to the container_apps module, which runs it in each replica.

- **A health token**: the Key Vault secret `pathways-health-token`, holding a bearer token the
  module generates. The token is generated by an ephemeral resource and written in a write-only
  argument, so neither the plan nor the state holds it. The app gives it to the engine as
  `PATHWAYS_HEALTH_TOKEN`, which the health endpoint reads by default, and to the collector, so
  `/metrics` stays authenticated. Raise `health_token_version` to write a new one, then restart the
  app's revision.
- **An Application Insights resource**, `appi-<name>`, workspace-based on the Log Analytics workspace
  you give, and its connection string as the Key Vault secret `pathways-metrics-connection-string`,
  which only the collector reads. The connection string lets a caller send telemetry and read
  nothing; it is in the state, as an attribute of the resource.
- **The collector's configuration** (`collector_config`): it scrapes
  `http://127.0.0.1:<health_port>/metrics` every 30 seconds inside the replica, keeps only the five
  families below (of the settlements, only those that failed), folds away their channel,
  destination and outcome labels, turns the two counters into what was added since the previous
  scrape, and sends them to Application Insights with the `azuremonitor` exporter. No channel or
  destination name leaves the replica.
- **Five metric alerts** on those custom metrics, in the `azure.applicationinsights` namespace,
  each calling `action_group_id` when it fires and when it resolves:

| Alert                | Metric                                              | Fires when                                                              |
| -------------------- | --------------------------------------------------- | ----------------------------------------------------------------------- |
| `store-down`         | `pathways_store_up`, maximum                        | no reading was 1 for `store_down_minutes` minutes (5)                   |
| `oldest-pending-age` | `pathways_oldest_pending_age_seconds`, minimum      | every reading above `oldest_pending_age_seconds` (600) for 5 minutes    |
| `queue-depth`        | `pathways_queue_depth`, minimum                     | every reading above `queue_depth_threshold` (1000) for 5 minutes        |
| `refused-messages`   | `pathways_messages_refused_total`, total            | more than `refused_messages_threshold` (0) in 15 minutes                |
| `settled-failed`     | `pathways_settled_destinations_total` (failed), total | more than `settled_failed_threshold` (0) in 15 minutes                |

Azure does not fire a metric alert on missing data, so a stopped engine or a stopped collector does
not fire `store-down`: it fires only while the engine reports that it cannot read its database. And
Azure takes a metric alert's window only from a fixed list, so `store_down_minutes` is 1, 5, 15, 30
or 60.

To use it on its own:

```hcl
module "alarms" {
  source = "github.com/cosyte/terraform-azurerm-pathways//modules/alarms"

  name                       = "pw-example"
  resource_group_name        = "rg-pathways-example"
  location                   = "eastus2"
  log_analytics_workspace_id = "<a Log Analytics workspace id>"
  key_vault_id               = "<a Key Vault you can write secrets to>"
  action_group_id            = "<an action group id>"
}
```

Then run an OpenTelemetry collector with the `prometheus` receiver, the `filter`,
`metricstransform` and `cumulativetodelta` processors and the `azuremonitor` exporter beside the
engine, with `collector_config` in `PATHWAYS_COLLECTOR_CONFIG` and `--config=env:PATHWAYS_COLLECTOR_CONFIG`,
and the two secrets in `PATHWAYS_HEALTH_TOKEN` and `APPLICATIONINSIGHTS_CONNECTION_STRING`, as the
container_apps module's `metrics_collector` does.

Inputs are in [variables.tf](variables.tf) and outputs in [outputs.tf](outputs.tf). Its tests are
in [tests/](tests), run by `tests/run.sh` at the repo root.
